# ターミナル・シェル・エディタの基礎知識

「ターミナル」「シェル」「コンソール」「エディタ」……似たような言葉がたくさん出てきて混乱しますよね。この章では、これらの違いを整理し、それぞれの選択肢を比較します。dotfiles を管理するうえでの前提知識として、まず全体像を掴んでおきましょう。

## 全体像 — 何がどこにいるのか

まずは大きな絵を見てください。

```
┌─────────────────────────────────────────────────────┐
│                   ターミナルエミュレータ                │
│  ┌───────────────────────────────────────────────┐  │
│  │                    シェル (zsh, bash, fish)     │  │
│  │                                               │  │
│  │  $ ls -la          ← コマンドを入力            │  │
│  │  $ vim config.yml  ← エディタを起動            │  │
│  │  $ python app.py   ← プログラムを実行          │  │
│  │                                               │  │
│  └───────────────────────────────────────────────┘  │
│                                                     │
│  フォント・色・透過度・ウィンドウサイズ = ターミナルの仕事  │
│  コマンド解釈・補完・環境変数・パイプ   = シェルの仕事    │
└─────────────────────────────────────────────────────┘
```

ポイントは **ターミナルとシェルは別物** ということです。

- **ターミナルエミュレータ**: 画面を描画するアプリケーション（見た目担当）
- **シェル**: コマンドを解釈・実行するプログラム（頭脳担当）
- **エディタ**: ファイルを編集するプログラム（シェルの中で動くことも、独立したアプリとしても使える）

もう少し身近な例えで説明すると:

```
ターミナル  = テレビ（映像を映す装置）
シェル      = テレビ番組（中身・コンテンツ）
エディタ    = 番組内で使う道具（テロップ編集ソフトみたいなもの）
```

テレビ（ターミナル）を買い替えても番組（シェル）は変わらないし、番組（シェル）を切り替えてもテレビ（ターミナル）はそのままです。それぞれ独立して選べます。

## ターミナルエミュレータ

### ターミナルエミュレータとは

昔のコンピュータには物理的な「端末（ターミナル）」がありました。キーボードとモニターだけの装置で、メインフレームに接続して使うものです。現代ではそれをソフトウェアで再現（エミュレート）しているので「ターミナルエミュレータ」と呼びます。普段は単に「ターミナル」と呼ぶことが多いです。

```
1970年代                              現代
┌──────────┐    ケーブル    ┌────┐    ┌──────────────────────┐
│ VT100    │───────────→│ 大型 │    │ ターミナルエミュレータ  │
│ (物理端末) │             │ 計算機│    │ (ソフトウェア)         │
└──────────┘             └────┘    │                      │
                                   │  同じ PC 上で         │
キーボード + ブラウン管              │  シェルと直接通信      │
                                   └──────────────────────┘
```

### 主なターミナルエミュレータの比較

| ターミナル | OS | GPU 描画 | タブ/分割 | 設定形式 | 特徴 |
|-----------|-----|---------|----------|---------|------|
| [WezTerm](https://wezfurlong.org/wezterm/) | Win/Mac/Linux | ✅ | ✅ | Lua | 設定の柔軟性が圧倒的 |
| [Alacritty](https://alacritty.org/) | Win/Mac/Linux | ✅ | ❌ | TOML | 最速レベル、機能は最小限 |
| [kitty](https://sw.kovidgoyal.net/kitty/) | Mac/Linux | ✅ | ✅ | conf | 画像表示対応、拡張性が高い |
| [Ghostty](https://ghostty.org/) | Mac/Linux | ✅ | ✅ | 独自 | ネイティブ UI、高性能 |
| [Windows Terminal](https://github.com/microsoft/terminal) | Win | ✅ | ✅ | JSON | Windows 標準、WSL 連携が優秀 |
| [iTerm2](https://iterm2.com/) | Mac | ❌ | ✅ | GUI | macOS の定番、機能が豊富 |
| [GNOME Terminal](https://gitlab.gnome.org/GNOME/gnome-terminal) | Linux | ❌ | ✅ | GUI | Ubuntu のデフォルト |
| [Terminal.app](https://support.apple.com/ja-jp/guide/terminal/welcome/mac) | Mac | ❌ | ✅ | GUI | macOS 標準、追加インストール不要 |

:::message
GPU 描画（GPU アクセラレーション）対応のターミナルは、大量のログ出力や高速スクロール時にカクつきにくいです。日常的にログを眺める人は GPU 対応のものを選ぶと快適です。
:::

### 選び方のフローチャート

```
ターミナルを選ぶ
  │
  ├─ Windows？
  │   ├─ WSL を使う → Windows Terminal（標準で WSL 対応）
  │   └─ もっとカスタマイズしたい → WezTerm
  │
  ├─ macOS？
  │   ├─ とりあえず使いたい → Terminal.app（最初から入ってる）
  │   ├─ 高機能がほしい → iTerm2（macOS ユーザーの定番）
  │   └─ 速さ重視 → Ghostty or WezTerm
  │
  └─ Linux？
      ├─ デフォルトで十分 → GNOME Terminal / Konsole
      ├─ 速さ重視 → Alacritty（最速、ただしタブなし）
      ├─ バランス重視 → kitty or Ghostty
      └─ 設定を極めたい → WezTerm（Lua で何でもできる）
```

### 各ターミナルの詳細

#### WezTerm — 設定の自由度が最高

**メリット:**
- Lua で設定を記述するため、条件分岐やループなどプログラマブルな設定が可能
- クロスプラットフォーム（Windows / macOS / Linux）
- タブ・ペイン分割・マルチプレクサ機能を内蔵
- Nerd Font のリガチャ対応

**デメリット:**
- Lua の学習コストがやや高い
- 設定ファイルがプログラムに近く、シンプルさを求める人には過剰

#### Alacritty — 速さこそ正義

**メリット:**
- 最速クラスの描画性能
- TOML で設定がシンプル
- 余計な機能がなく、やることが明確

**デメリット:**
- タブもペイン分割もない（tmux 等と組み合わせる前提）
- GUI 設定なし、すべて設定ファイルで管理

#### Ghostty — 新世代のターミナル

**メリット:**
- Zig 製で非常に高速
- ネイティブ UI（macOS は Cocoa、Linux は GTK）で OS に溶け込む
- ゼロコンフィグでもすぐ使える

**デメリット:**
- 比較的新しく、エコシステムが発展途上
- Windows 版は未リリース（2026年3月時点）

## シェル

### シェルとは

シェルは、ユーザーが入力したコマンドを解釈してカーネル（OS の中核）に伝えるプログラムです。「殻（シェル）」という名前は、カーネル（核）を包む殻というイメージから来ています。

```
┌───────────────────────────────────────┐
│              ユーザー                  │
│         「ファイル一覧見せて」          │
│                 │                     │
│                 ▼                     │
│  ┌───────────────────────────┐       │
│  │    シェル (zsh, bash...)    │ ← 殻  │
│  │  ・コマンドの解釈            │       │
│  │  ・パイプ・リダイレクト処理   │       │
│  │  ・変数・関数管理            │       │
│  │  ・補完・履歴               │       │
│  └─────────────┬─────────────┘       │
│                 │                     │
│                 ▼                     │
│  ┌───────────────────────────┐       │
│  │      カーネル (Linux)       │ ← 核  │
│  │  ・プロセス管理              │       │
│  │  ・ファイルシステム           │       │
│  │  ・メモリ管理               │       │
│  └───────────────────────────┘       │
└───────────────────────────────────────┘
```

### 主なシェルの比較

| シェル | 登場年 | 特徴 | 設定ファイル |
|-------|-------|------|------------|
| [bash](https://www.gnu.org/software/bash/) | 1989 | Linux の標準、情報量が圧倒的 | `.bashrc` |
| [zsh](https://www.zsh.org/) | 1990 | bash 上位互換、macOS 標準 | `.zshrc` |
| [fish](https://fishshell.com/) | 2005 | 設定不要で便利、独自構文 | `config.fish` |
| [nushell](https://www.nushell.sh/) | 2019 | データ指向、テーブル出力 | `config.nu` |
| [PowerShell](https://github.com/PowerShell/PowerShell) | 2006 | オブジェクト指向、Windows 標準 | `$PROFILE` |

### 各シェルの詳細

#### bash — 安定と互換性の王

```
$ echo "Hello, World!"
Hello, World!
```

**メリット:**
- ほぼすべての Linux / macOS にプリインストール
- シェルスクリプトの事実上の標準（`#!/bin/bash`）
- 情報量が圧倒的に多い（StackOverflow、ブログ、書籍）
- サーバー管理では bash を知っていれば困らない

**デメリット:**
- 補完やシンタックスハイライトはデフォルトでは貧弱
- プラグインエコシステムがほぼない
- 対話的な使い勝手は zsh や fish に劣る

**こんな人におすすめ:** サーバー管理がメイン、スクリプトの互換性を重視する人

#### zsh — バランスの良い万能選手

```
$ ls **/*.md          # 再帰グロブ（bash では shopt が必要）
$ cd /u/l/b[TAB]      # → /usr/local/bin（あいまい補完）
```

**メリット:**
- bash とほぼ互換（bash のスクリプトがだいたい動く）
- 強力な補完システム（`compinit`）
- 豊富なプラグインエコシステム（oh-my-zsh, sheldon 等）
- macOS Catalina 以降のデフォルトシェル

**デメリット:**
- 設定しないと bash とあまり変わらない（設定して初めて真価を発揮）
- プラグインを入れすぎると起動が遅くなる（→ zsh-defer で対策可能）

**こんな人におすすめ:** 対話的な操作も、スクリプトの互換性も両方ほしい人（この Book ではこれを採用）

#### fish — 設定いらずですぐ便利

```
$ ls *.md            # ファイル名がリアルタイムで色付き表示
$ git com[TAB]       # → commit（マニュアルを解析して自動補完）
```

**メリット:**
- インストールした瞬間からシンタックスハイライト、自動補完が使える
- Web ベースの設定 UI（`fish_config`）
- エラーメッセージが親切で分かりやすい

**デメリット:**
- POSIX 非互換（bash のスクリプトがそのまま動かない）
- `&&` の代わりに `; and`、`||` の代わりに `; or` など独自構文
- bash / zsh 向けの `.env` ファイルや設定例がそのまま使えない

**こんな人におすすめ:** 設定に時間をかけたくない人、シェルスクリプトをあまり書かない人

#### nushell — 次世代のデータ指向シェル

```
> ls | where size > 1mb | sort-by modified
╭───┬──────────────┬──────┬───────────╮
│ # │     name     │ size │ modified  │
├───┼──────────────┼──────┼───────────┤
│ 0 │ video.mp4    │ 24MB │ yesterday │
│ 1 │ archive.tar  │ 3MB  │ 2 days    │
╰───┴──────────────┴──────┴───────────╯
```

**メリット:**
- コマンドの出力が構造化データ（テーブル）として扱える
- パイプラインでフィルタ・ソート・集計が直感的
- エラーメッセージが Rust 風で非常に分かりやすい

**デメリット:**
- bash / zsh とは全く異なる構文
- 既存のシェルスクリプト資産は使えない
- まだ発展途上で破壊的変更があり得る

**こんな人におすすめ:** データ処理が多い人、従来のシェルに不満がある人

### シェルの選び方

```
シェルを選ぶ
  │
  ├─ サーバー管理がメイン？
  │   └─ bash（どこでも動く安心感）
  │
  ├─ 設定は最小限で便利に使いたい？
  │   └─ fish（箱から出してすぐ便利）
  │
  ├─ bash 互換 + 高機能がほしい？
  │   └─ zsh（この Book のおすすめ）
  │
  └─ 新しいパラダイムに挑戦したい？
      └─ nushell（データ指向の新世界）
```

:::message
どのシェルを選んでも、**bash の基本構文は覚えておくべき**です。CI/CD、Docker、サーバー管理ではほぼ bash が前提です。日常の対話シェルは好きなものを、スクリプトは bash で書く、という使い分けが現実的です。
:::

## エディタ

### エディタの分類

エディタは大きく 3 種類に分けられます。

```
エディタの分類
  │
  ├─ ターミナルエディタ（CUI）
  │   ターミナルの中で動く
  │   例: vim, neovim, nano, emacs (CUI), helix
  │
  ├─ GUI エディタ
  │   独立したウィンドウで動く
  │   例: VS Code, Zed, Cursor, Sublime Text
  │
  └─ IDE（統合開発環境）
      エディタ + デバッガ + ビルドツール等が一体化
      例: IntelliJ IDEA, PyCharm, Xcode, Visual Studio
```

### 主なエディタの比較

| エディタ | 種類 | 起動速度 | 学習コスト | 拡張性 | 特徴 |
|---------|------|---------|----------|-------|------|
| [Vim](https://www.vim.org/) / [Neovim](https://neovim.io/) | CUI | ⚡ 最速 | 📈 高い | 🔧 非常に高い | モーダル編集の元祖 |
| [Helix](https://helix-editor.com/) | CUI | ⚡ 最速 | 📈 やや高い | 🔧 中程度 | モダンな Vim 代替 |
| [nano](https://www.nano-editor.org/) | CUI | ⚡ 最速 | 📉 低い | 🔧 低い | シンプルで直感的 |
| [Emacs](https://www.gnu.org/software/emacs/) | CUI/GUI | 🐢 遅い | 📈 非常に高い | 🔧 無限 | 「OS の中の OS」 |
| [VS Code](https://code.visualstudio.com/) | GUI | 🚶 普通 | 📉 低い | 🔧 非常に高い | 拡張機能の王様 |
| [Zed](https://zed.dev/) | GUI | ⚡ 速い | 📉 低い | 🔧 発展中 | Rust 製で高速 |
| [Cursor](https://www.cursor.com/) | GUI | 🚶 普通 | 📉 低い | 🔧 高い | AI ファーストなエディタ |
| [Sublime Text](https://www.sublimetext.com/) | GUI | ⚡ 速い | 📉 低い | 🔧 高い | 軽量で速い老舗 |

### ターミナルエディタ vs GUI エディタ

```
ターミナルエディタ                     GUI エディタ
┌─────────────────────┐            ┌─────────────────────┐
│ $ vim config.yml    │            │ ┌─ VS Code ────────┐ │
│                     │            │ │ ファイルツリー │本文│ │
│ server:             │            │ │               │   │ │
│   port: 8080█       │            │ │ 拡張機能      │   │ │
│   host: 0.0.0.0     │            │ │               │   │ │
│ ~                   │            │ │ ──────────────│   │ │
│ ~                   │            │ │ ターミナル     │   │ │
│ -- INSERT --        │            │ └───────────────────┘ │
└─────────────────────┘            └─────────────────────┘
SSH 先でもそのまま使える             マウスで直感的に操作できる
```

| 比較項目 | ターミナルエディタ | GUI エディタ |
|---------|-----------------|-------------|
| SSH / リモート作業 | ◎ そのまま使える | △ リモート接続機能が必要 |
| 起動速度 | ◎ 一瞬で起動 | ○〜△ アプリにより異なる |
| 直感的な操作 | △ 操作を覚える必要がある | ◎ マウスで直感的 |
| ファイルツリー | △ プラグインが必要 | ◎ 標準搭載 |
| デバッガ統合 | △ 設定が必要 | ◎ ボタンひとつ |
| dotfiles との相性 | ◎ 設定ファイルで完結 | ○ JSON 等で管理 |

### 各エディタの詳細

#### Vim / Neovim — 速度と効率の極致

**モーダル編集**が最大の特徴です。「入力モード」と「操作モード」を切り替えて使います。

```
ノーマルモード           インサートモード
┌─────────────┐        ┌─────────────┐
│ カーソル移動  │   i    │ 文字入力     │
│ コピー・削除  │ ────→ │ 普通のエディタ │
│ 検索・置換   │ ←──── │ のように入力  │
│             │  Esc   │             │
└─────────────┘        └─────────────┘
```

**メリット:**
- ホームポジションから手を動かさずにあらゆる操作が可能
- 起動が一瞬、SSH 先でもすぐ使える
- 慣れると編集速度が圧倒的に速い
- Neovim は Lua で設定でき、モダンな開発環境を構築可能

**デメリット:**
- 学習曲線が急（最初は `:q` で終了する方法すら分からない）
- 設定を育てる時間が必要（特に Neovim の LSP 設定等）
- 「Vim 沼」にハマると設定ファイルの調整が止まらなくなる

#### nano — とにかくシンプル

**メリット:**
- 画面下部に操作方法が表示される（迷わない）
- 覚えることが少ない（`Ctrl+O` で保存、`Ctrl+X` で終了）
- ほぼすべての Linux にプリインストール

**デメリット:**
- 高度な編集機能は期待できない
- 大きなファイルの編集には不向き

**こんな人におすすめ:** サーバーで設定ファイルをちょっと編集するだけの人、Vim の操作を覚えたくない人

#### VS Code — 拡張機能エコシステムの王者

**メリット:**
- 拡張機能が数万種類あり、どんな言語・フレームワークにも対応
- 統合ターミナル、デバッガ、Git 連携が標準搭載
- Remote SSH / WSL / Dev Container でリモート開発が快適
- 学習コストが低く、すぐに使い始められる

**デメリット:**
- Electron ベースなのでメモリ消費が多い（1GB 以上使うことも）
- 起動がやや遅い
- 拡張機能を入れすぎると重くなる

#### Zed — 速さとシンプルさの両立

この Book の Zed エディタチャプターで詳しく解説しています。

**メリット:**
- Rust 製 + GPU レンダリングで非常に高速
- AI 統合が組み込み
- VS Code に近い操作感で移行しやすい

**デメリット:**
- 拡張機能エコシステムは発展途上
- 特定の言語サポートが VS Code より手薄な場合がある

### エディタの選び方

```
エディタを選ぶ
  │
  ├─ サーバーで設定ファイルを編集するだけ？
  │   └─ nano（一番簡単）or vim（覚える価値あり）
  │
  ├─ ターミナルで完結したい？
  │   ├─ 効率を極めたい → Neovim
  │   └─ モダンに始めたい → Helix
  │
  ├─ GUI で快適に開発したい？
  │   ├─ 拡張機能重視 → VS Code
  │   ├─ 速度重視 → Zed
  │   └─ AI 重視 → Cursor
  │
  └─ とりあえず迷ったら？
      └─ VS Code（情報量・拡張機能・コミュニティが最大）
```

:::message
Vim のキーバインドは多くのエディタで使えます（VS Code の Vim 拡張、Zed の Vim モード等）。Vim 自体を使わなくても、Vim のキーバインドを覚えておくと、どのエディタでも編集効率が上がります。
:::

## ターミナルマルチプレクサ

### ターミナルマルチプレクサとは

ターミナルマルチプレクサは、**1 つのターミナルウィンドウ内で複数のセッションを管理**するツールです。

```
通常のターミナル                  マルチプレクサ使用時
┌──────────┐                  ┌──────────────────────┐
│          │                  │ ペイン1  │ ペイン2    │
│ 1つの    │                  │ vim     │ サーバー   │
│ シェルだけ │                  │         │ ログ      │
│          │                  │─────────┼──────────│
│          │                  │ ペイン3               │
│          │                  │ $ git status          │
└──────────┘                  ├──────────────────────┤
                              │ [0] main  [1] server │
                              └──────────────────────┘
                              ↑ ウィンドウ（タブ）切替
```

### なぜ必要なのか

マルチプレクサが真価を発揮するのは、主に以下のケースです:

1. **SSH 接続が切れてもプロセスが生き続ける**（セッション永続化）
2. **1 画面でエディタ + サーバー + ログを同時に見られる**（ペイン分割）
3. **複数プロジェクトをウィンドウ（タブ）で切り替えられる**

```
SSH 接続が切れたとき:

通常の SSH:
  PC ──✕── サーバー  → 実行中のプロセスが終了 😢

マルチプレクサ使用:
  PC ──✕── サーバー  → tmux セッションは生き続ける
  PC ──再接続── サーバー → tmux attach で復帰 😊
```

### 主なマルチプレクサの比較

| ツール | 登場年 | 言語 | 設定形式 | 特徴 |
|--------|-------|------|---------|------|
| [tmux](https://github.com/tmux/tmux) | 2007 | C | `.tmux.conf` | 最も普及、情報が豊富 |
| [Zellij](https://zellij.dev/) | 2021 | Rust | KDL | 初心者に優しい UI |
| [screen](https://www.gnu.org/software/screen/) | 1987 | C | `.screenrc` | 最古参、レガシー環境向け |

#### tmux — 定番のマルチプレクサ

```
$ tmux                    # 新しいセッションを開始
$ tmux new -s project     # 名前付きセッションを開始
$ tmux attach -t project  # セッションに再接続
$ tmux ls                 # セッション一覧
```

**メリット:**
- ほぼすべてのサーバーにインストール可能
- 情報量が圧倒的に多い
- プラグインエコシステム（tpm）がある
- ステータスバーのカスタマイズ性が高い

**デメリット:**
- キーバインドが直感的でない（`Ctrl+B` プレフィックス）
- 設定ファイルの構文がやや独特
- 初心者には操作方法が分かりにくい

**主要なキーバインド（デフォルト）:**

| キー | 動作 |
|------|------|
| `Ctrl+B` → `%` | 画面を左右に分割 |
| `Ctrl+B` → `"` | 画面を上下に分割 |
| `Ctrl+B` → `矢印キー` | ペイン間を移動 |
| `Ctrl+B` → `c` | 新しいウィンドウを作成 |
| `Ctrl+B` → `n` | 次のウィンドウへ |
| `Ctrl+B` → `d` | セッションからデタッチ |

#### Zellij — モダンで初心者に優しい

```
$ zellij                  # 開始（操作ガイドが画面下に表示される）
$ zellij attach project   # セッションに再接続
```

**メリット:**
- 画面下部に操作可能なキーが常に表示される（迷わない）
- デフォルト設定でも十分使いやすい
- レイアウトをファイルで定義できる
- プラグインシステム（WebAssembly）

**デメリット:**
- tmux に比べると普及率が低い
- 古いサーバーにはインストールしにくい
- tmux ほどのカスタマイズ自由度はない

### マルチプレクサが不要なケース

最近のターミナルエミュレータはタブやペイン分割を内蔵しているため、以下の場合はマルチプレクサなしでも快適です:

```
マルチプレクサが必要？
  │
  ├─ SSH でリモートサーバーに接続する？
  │   ├─ はい → tmux を使うべき（セッション永続化のため）
  │   └─ いいえ ↓
  │
  ├─ ターミナルにタブ/分割機能がある？
  │   ├─ はい（WezTerm, kitty 等）→ マルチプレクサなしでも OK
  │   └─ いいえ（Alacritty 等）→ tmux or Zellij を使う
  │
  └─ エディタに統合ターミナルがある？
      ├─ はい（VS Code, Zed 等）→ エディタ内で完結も可能
      └─ いいえ → マルチプレクサを検討
```

:::message
Alacritty のように「タブもペイン分割もない」ターミナルを選ぶ場合は、tmux や Zellij とセットで使うのが定番の組み合わせです。逆に WezTerm や kitty はマルチプレクサの機能を内蔵しているので、ローカル作業ならマルチプレクサなしでも快適に使えます。
:::

## おすすめの組み合わせ

ここまで紹介したツールは自由に組み合わせられます。参考として、いくつかの組み合わせパターンを紹介します。

### パターン 1: ミニマリスト

```
Alacritty（ターミナル）
  └─ tmux（マルチプレクサ）
       └─ zsh（シェル）+ Neovim（エディタ）
```

すべてターミナル内で完結。設定ファイルだけで環境を再現できる。dotfiles との相性が最高。

### パターン 2: モダンバランス型（この Book の構成）

```
任意のターミナル
  └─ zsh + sheldon（シェル + プラグイン管理）
       └─ Zed（GUI エディタ）+ 統合ターミナル
```

GUI エディタの快適さとシェル環境のカスタマイズを両立。

### パターン 3: 初心者フレンドリー

```
Windows Terminal / iTerm2（ターミナル）
  └─ fish（シェル、設定不要で便利）
       └─ VS Code（GUI エディタ）
```

すべて「すぐ使える」ものを選択。学習コストが最小限。

### パターン 4: フルカスタマイズ

```
WezTerm（ターミナル、Lua で設定）
  └─ zsh + sheldon（シェル）
       ├─ Neovim（ターミナルエディタ、Lua で設定）
       └─ tmux（マルチプレクサ）
```

すべてを設定ファイルで管理。dotfiles で完全に環境を再現できる上級者向け。

## まとめ

```
┌──────────────┬──────────────────────────────────────┐
│ カテゴリ      │ 覚えておくこと                        │
├──────────────┼──────────────────────────────────────┤
│ ターミナル    │ 見た目担当。好みで選んでよい            │
│ シェル        │ 頭脳担当。bash の知識は必須            │
│ エディタ      │ 開発スタイルで選ぶ。Vim 操作は汎用的    │
│ マルチプレクサ │ SSH 使うなら必須。ローカルなら任意      │
└──────────────┴──────────────────────────────────────┘
```

それぞれが独立したレイヤーなので、**一度に全部を決める必要はありません**。まずはデフォルトのターミナルと bash / zsh で始めて、不便を感じたら一つずつ入れ替えていく、というアプローチがおすすめです。

この Book では zsh + sheldon + Zed という構成を採用していますが、これが唯一の正解というわけではありません。自分の作業スタイルに合ったツールを選んで、dotfiles で管理していきましょう。
