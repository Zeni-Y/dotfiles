# Zenn Book 執筆ガイドライン

## Writing Style（文体・トーン）

筆者の既存ブログ（「研究のためのPython開発環境」）から抽出したスタイル。
このトーンに合わせて執筆すること。

### 基本トーン

- 「です・ます」調をベースにしつつ、**カジュアルで親しみやすい口調**を混ぜる
- 硬すぎない。教科書ではなく、先輩が後輩に教える感覚
- 個人的な意見・感想は率直に書く（「個人的感想を含みます」「体感〜な気がします」）

### OK な表現（筆者のスタイルに合うもの）

- 「めちゃめちゃ便利です」「使わない手はないと思います」
- 「〜ですね」「〜ですよね」（語尾で親しみを出す）
- 「〜のはめんどくさいので」（率直な感想）
- 「（正気か？）」「すごくないですか？」（感嘆・ツッコミ）
- 「そんなあなたに〜」（読者への直接的な呼びかけ）
- 括弧内での補足: 「（体感の認知度低いですがめちゃめちゃ便利です。）」

### NG な表現（筆者のスタイルに合わないもの）

- 過度にフォーマルな表現: 「〜でございます」「〜いたします」
- 淡々とした説明だけの文章（感想や意見がないと味気ない）
- 「本項では〜について述べる」のような論文調
- 「ぶっちゃけ」（カジュアルすぎる）

### 見出しの付け方

- 口語的でストレートな見出しも OK: 「# それで結局どういう流れで使うんですか」「# 結局やること」
- ツール名はそのまま英語で: 「# [Poetry](URL)」
- 長すぎない

### 段落・テンポ

- 1段落は短め（2〜4文）。長い説明は箇条書きや :::details で分割する
- コードブロックの前は簡潔に1文で導入: 「以下のコマンドで〜します。」
- 補足が長くなりそうなら `:::details` で折りたたむ

### リンクの扱い

- URLはそのまま貼らず、その記事のタイトルにハイパーリンクを付ける。
  - [age-encryption.org/v1 — age 公式仕様](https://age-encryption.org/v1)等

### 個人的な意見の入れ方

- 「個人的な意見です」「完全好みです」のように断りを入れてから書く
- 「まさかり大歓迎です」のように、間違いがあれば指摘してほしいスタンス
- 体験談は自然に混ぜる: 「筆者は〜しています」「自分も〜なところがあるのですが」

## 参考文献・引用ルール

### 原則

- 技術的な主張（仕様・内部実装・セキュリティ特性など）を記述する際は、信頼できる情報源の引用を付けること。
- 初出のツールや技術に関しては説明を付けること。

### 引用が必要なケース

1. **暗号・セキュリティに関する技術的主張**（例: 「age は scrypt を KDF として使用」）
2. **ツールの内部仕様・設計判断**（例: 「chezmoi は Go template を使用」）
3. **パフォーマンス数値や比較データ**
4. **公式ドキュメントに基づく仕様説明**

### 引用が不要なケース

1. **CLI の使い方**（`chezmoi add --encrypt` 等、実行すれば確認できるもの）
2. **一般的な知識**（「SSH 鍵は秘密にすべき」等）
3. **筆者自身の設計判断や意見**

### 引用の書き方

チャプター末尾に `## 参考文献` セクションを設け、番号付きリストで記載する。
本文中では `[^1]` 等の脚注記法、または文脈に応じてインラインリンクで参照する。

```markdown
## 参考文献

[^1]: [age 公式仕様 (age-encryption.org/v1)](https://age-encryption.org/v1)
[^2]: [chezmoi ドキュメント](https://www.chezmoi.io/)
```

### 信頼できる情報源の優先順位

1. **公式仕様書・RFC**（最も信頼性が高い）
2. **公式ドキュメント・README**
3. **ソースコード**（実装の裏付けとして）
4. **作者によるブログ・設計文書**
5. **信頼性の高い技術記事**

## 技術選定・設計の理念

- **必要十分でシンプル**: 技術選定は、必要十分な技術で可能な限りシンプルでわかりやすいことを重視する
- **後から見返せること**: ショートカットやライフサイクルなど、複雑で忘れやすい知識は必ずメモやチートシートを残し、後で誰でも見返して分かるようにする
- この理念は技術を紹介する際の判断基準としても反映する（例: 「GPG より age を選ぶ理由」はシンプルさが決め手）

## 概観→具体の原則

ツールや仕組みを解説するチャプターでは、**いきなり具体的な設定やコマンドの説明に入らない**こと。読者は前提知識がない状態で読み始めるため、まず以下の順序で概観を示してから具体に入る。

### 解説の順序

1. **そのツール/仕組みが解決する課題** — 何が不便で、何を解決するためにあるのか
2. **設計思想・アプローチ** — どういう考え方で課題を解決しているのか（例: 「コピーベース vs symlink ベース」「宣言的 vs 手続き的」）
3. **管理対象と全体像** — 何をどのように管理しているのか、登場する概念の関係性
4. **ライフサイクル（概要）** — 初回セットアップ → 日常の変更 → 反映、のような大まかな流れ
5. **具体的な使い方** — コマンド、設定ファイル、コード例

### NG パターン

- 「`.chezmoi.yaml.tmpl` でカスタムデータを定義しています」← カスタムデータとは何か、なぜ必要なのかの説明がない
- 「`run_once_before_` で〜を実行します」← chezmoi apply の全体フローを示す前に個別の機能を説明している
- 初出の用語にリンクや説明がない（例: Stow、symlink ベース）

### OK パターン

```markdown
## chezmoi テンプレートとは

chezmoi の dotfiles 管理には「1つのソースから、環境ごとに異なる設定ファイルを生成したい」
という課題があります。たとえば macOS と Linux で異なるパスを使いたい、
client と server で異なるプラグインを読み込みたい、といったケースです。

chezmoi はこの課題を **Go template** で解決しています。
ソースファイルにテンプレート構文を埋め込み、`chezmoi apply` 時に
環境に応じた値に展開してからファイルを配置します。

（ここから具体的な構文説明に入る）
```

## ステップ・手順の書き方

複数のステップからなるセットアップや操作手順を説明する場合、以下を守ること。

### 全体像を先に示す

手順が3ステップ以上ある場合、最初にフロー図や番号付きリストで**全体の流れを俯瞰**させる。読者が「今どこにいるか」「あと何をすればいいか」を常に把握できるようにする。

```
Step 1: ○○を生成
         ↓ △△が得られる
Step 2: △△を使って□□を設定
         ↓ ☆☆ができる状態になる
Step 3: ☆☆を実行
```

### 各ステップで明示すべき3要素

1. **何を実行するか** — 具体的なコマンドや操作
2. **何が得られるか** — 実行結果、生成されるファイル、出力例
3. **次のステップとの接続** — 得られたものが次にどう使われるか

```markdown
### Step 1: age 鍵ペアの生成

以下のコマンドで鍵ペアを生成します。

（コマンド）

実行すると、公開鍵が画面に表示されます。

（出力例）

この**公開鍵**を次の Step 2 で `.chezmoi.yaml.tmpl` に記載します。
```

### やりがちな NG パターン

- コマンドだけ並べて「何が起きるか」の説明がない
- 前のステップの結果が次のステップのどこに使われるか不明
- 途中の分岐（エラー時の対処等）が無視されている

### チャプター末尾にライフサイクルセクションを設ける

ツールや仕組みを解説するチャプターでは、末尾に **日常的な使い方（ライフサイクル）** をまとめたセクションを設ける。読者が「で、結局どういう場面でどのコマンドを叩くの？」を一目で分かるようにする。

含めるべき内容:
1. **初期セットアップ** — 初回だけ必要な手順
2. **日常の操作** — 普段のワークフローで頻繁に使うコマンド
3. **メンテナンス** — 更新・変更時に必要な手順

```markdown
## ライフサイクル

### 初期セットアップ（初回のみ）

（コマンドとその説明）

### 日常の操作

| やりたいこと | コマンド |
|------------|---------|
| ○○する | `xxx` |
| △△する | `yyy` |

### 設定を変更したいとき

（手順）
```

チャプターの内容が概念説明中心（例: クロスプラットフォームの分岐モデル、セキュリティの設計思想）の場合は不要。あくまで**ツールの実際の使い方**が主題のチャプターに適用する。

## その他の執筆ルール

### コードブロック

- 言語を明示する（```bash, ```yaml, ```toml 等）
- 実行例にはコメントで補足を付ける

### 情報量のコントロール

- 1つのセクションが長くなりすぎる場合は、**要点だけ本文に残し、詳細は `:::details` で折りたたむ**
- 目安: 表が2つ以上連続する場合や、補足的な内容が主題より長くなる場合は折りたたみを検討する
- 折りたたみのタイトルは中身が想像できるものにする（例: 「その他のキーバインド」「設定の詳細」）

### Zenn 記法

- 注意書き: `:::message` / `:::message alert`
- 詳細折りたたみ: `:::details タイトル`
- URL カード: URL を単独行に貼る（自動でカード表示される）
